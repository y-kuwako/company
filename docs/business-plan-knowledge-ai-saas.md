# 事業計画書: ナレッジAI SaaS「KnowHub」

## エグゼクティブサマリー

**プロダクト名**: KnowHub（仮称）
**コンセプト**: 「書かなくても溜まるナレッジAI」
**ターゲット**: 従業員50〜200人の日本企業
**価格帯**: 月額3〜10万円
**空白地帯**: 手軽な価格 x RAG対話型AI を両立する製品が国内市場に不在

---

## 1. MVP設計

### 1.1 最小機能セット（5機能）

| # | 機能 | 概要 | 優先度 |
|---|------|------|--------|
| 1 | **Slack/Teams連携 自動ナレッジ収集** | 指定チャンネルの会話を自動で取り込み、要約・構造化してナレッジ化。「書かなくても溜まる」の中核機能 | 必須 |
| 2 | **RAG対話型AI検索** | 蓄積されたナレッジに対して自然言語で質問し、出典付きで回答を得られるチャットUI | 必須 |
| 3 | **ドキュメント手動アップロード** | PDF・Word・Google Docs等の既存文書をアップロードしてナレッジベースに追加 | 必須 |
| 4 | **管理画面（テナント管理）** | ユーザー管理、取り込みソース設定、利用状況ダッシュボード | 必須 |
| 5 | **回答フィードバック機能** | AIの回答に対する「役に立った/立たなかった」評価。RAG精度改善のデータ収集 | 重要 |

**MVPで意図的に含めないもの**:
- Notion/Confluence連携（v1.1以降）
- 高度な権限管理・SSO（v1.2以降）
- カスタムAIモデルファインチューニング（v2.0以降）

### 1.2 技術スタック

| レイヤー | 技術 | 選定理由 |
|----------|------|----------|
| フロントエンド | Next.js 14 (App Router) + TypeScript | 請負チームのスキルセットと一致。SSR/ISRでSEO対応も可能 |
| UIライブラリ | shadcn/ui + Tailwind CSS | 高速なUI構築。デザインシステムの再利用性 |
| バックエンド | Next.js API Routes + tRPC | フロントと同一リポジトリで開発効率最大化 |
| データベース | PostgreSQL (Supabase) | マルチテナント対応。Supabaseで認証・Storageも一括管理 |
| ベクトルDB | Supabase pgvector | PostgreSQL内で完結。別サービス不要でコスト抑制 |
| AI/LLM | OpenAI API (GPT-4o-mini メイン / GPT-4o フォールバック) | コスパ最良。日本語性能が安定 |
| Embedding | OpenAI text-embedding-3-small | 低コストで十分な精度 |
| Slack連携 | Slack Bolt (Node.js SDK) | 公式SDK。イベントサブスクリプション対応 |
| Teams連携 | Microsoft Bot Framework SDK | 公式推奨。Webhook対応 |
| ファイル処理 | LangChain Document Loaders | PDF/Word/テキストの統一的なチャンク分割 |
| インフラ | Vercel (アプリ) + Supabase (DB/Auth/Storage) | サーバーレスで運用負荷最小。スケール自動 |
| ジョブキュー | Inngest or QStash (Upstash) | Slack取り込みの非同期処理。Vercel Serverlessと相性良好 |
| 監視 | Sentry + Vercel Analytics | エラー検知と利用分析 |

## 3. リスクと対策

### リスク1: RAGの回答精度が顧客の期待に届かない

| | 内容 |
|--|------|
| **影響度** | 高（解約に直結） |
| **発生確率** | 中〜高（日本語・社内用語特有の課題） |
| **対策** | (1) β期間に5社以上の実データで精度検証し、チューニングを重ねる。(2) チャンク分割戦略を複数パターン用意し、テナントごとに最適化可能にする。(3) フィードバック機能のデータを使い、月次で検索精度を改善するオペレーションを確立する。(4) 回答に必ず「出典リンク」を表示し、ユーザーが原文を確認できる安心設計にする |

### リスク2: 大手プレイヤーの参入（Microsoft Copilot、Google等）

| | 内容 |
|--|------|
| **影響度** | 高（市場そのものが変わる） |
| **発生確率** | 高（時間の問題） |
| **対策** | (1) 大手が手を出しにくい「日本企業の商習慣・日本語特化」で差別化。(2) 50〜200人規模の「大手ツールは高すぎるが、無料ツールでは不十分」な層に特化。(3) 導入の手軽さ（Slack連携のみで即利用開始）で先行獲得し、スイッチングコストを積み上げる。(4) 蓄積されたナレッジデータ自体がロックインになる |

### リスク3: 顧客獲得コスト（CAC）が想定を上回り、収益化が遅延する

| | 内容 |
|--|------|
| **影響度** | 中〜高（キャッシュフロー悪化） |
| **発生確率** | 中（中小企業向けSaaSの一般的課題） |
| **対策** | (1) 請負顧客からの紹介を最重要チャネルとし、CACゼロの顧客基盤を最大活用。(2) 初期は無料トライアル + ホワイトグローブオンボーディングで確実に定着させ、口コミ・事例を作る。(3) コンテンツマーケティング（「ナレッジ管理の課題と解決策」系記事）でSEO流入を確保。(4) 月額3万円のStarterプランで導入ハードルを極限まで下げ、社内稟議を通しやすくする |

## 4. 請負事業とのシナジー

### 4.1 顧客パイプラインの相互活用

```
請負顧客（大手企業）
  ├→ 大手の子会社・関連会社（50〜200人規模）にKnowHubを紹介
  ├→ 請負案件の中で「ナレッジ管理どうしてます？」とヒアリング → リード獲得
  └→ 請負の提案書に「自社プロダクトKnowHub導入済み」で信頼性向上

KnowHub顧客（中小企業）
  ├→ Webアプリ開発ニーズが出たら請負案件として受注
  ├→ 「KnowHubと連携するカスタム機能開発」で追加請負案件を獲得
  └→ 月額課金の安定収益が請負の売上の谷を埋める
```

### 4.2 技術・ノウハウの共有

| 請負 → KnowHub | KnowHub → 請負 |
|----------------|----------------|
| 大手案件で得たエンタープライズ品質の設計力 | RAG/AI技術の知見が請負提案の武器になる |
| 多様な業界知識（製造、金融、小売等）がプロダクト改善に活きる | SaaS運用で得たインフラ自動化ノウハウを請負に還元 |
| 外注エンジニアの稼働調整（請負の谷間にKnowHub開発を割り当て） | 自社プロダクトがエンジニア採用のアピール材料になる |

### 4.3 経営面のシナジー

- **収益の安定化**: 請負（変動収益）+ SaaS（月額定期収益）のハイブリッドでキャッシュフローが安定
- **企業価値の向上**: SaaS事業はARRベースでバリュエーションされるため、将来の資金調達・M&Aで有利
- **エンジニアの定着**: 「請負だけ」より「自社プロダクトもある」方が採用・定着に圧倒的に有利
- **開発リソースの柔軟配分**: 請負案件が少ない時期にKnowHub開発を加速。請負繁忙期はKnowHubを保守モードに

### 4.4 具体的なアクション

1. **月1回**: 請負の営業/PMが顧客との定例で「ナレッジ管理の課題」をヒアリング（所要5分）
2. **四半期1回**: 請負顧客向けにKnowHubの事例共有セミナーを開催（オンライン30分）
3. **随時**: KnowHub導入企業から開発案件の相談があれば、請負チームに即座にパス

## 6. 撤退基準

以下のいずれかに該当する場合、事業の継続可否を再検討する:

- **Month 9時点で有料顧客5社未満**: プロダクト-マーケットフィットが得られていない
- **Month 12時点でチャーン率5%超が3ヶ月連続**: プロダクトの価値が定着していない
- **Month 18時点で月次黒字化の見通しが立たない**: ユニットエコノミクスが成立しない
- **累計投資額が1,500万円を超えても月次BEP未達**: 追加投資の正当性がない
